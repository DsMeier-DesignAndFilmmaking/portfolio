# Field Guide Publishing System

## Purpose

This document defines a reusable publishing system for downloadable field guides within the Independent Systems Design Practice.

The goal is not to write a single guide yet. The goal is to create the content architecture, page model, visual hierarchy, component system, and distribution strategy that can support an expanding library of practice publications across:

- Architecture of Confidence
- Environmental Systems Design OS
- Responsive Ecologies
- Adaptive Outdoor Hospitality Companion
- Wayfinding Matrix
- Trust Frameworks for AI
- HADE product surfaces
- Future systems audits, scorecards, frameworks, and method kits

The field guide library should become a durable practice asset: part research publication, part consulting pre-read, part lead-generation artifact, and part proof of method.

## Strategic Role

Field guides should perform five jobs:

| Job | Meaning |
|---|---|
| Codify method | Turn implicit practice knowledge into repeatable frameworks. |
| Build authority | Demonstrate rigorous thinking without relying on portfolio aesthetics. |
| Support consulting | Give prospects a tangible way to understand the practice before a scoping call. |
| Create reusable IP | Convert frameworks into portable, citeable, downloadable assets. |
| Power publishing | Create a repeatable format for articles, PDFs, talks, workshops, and service collateral. |

## Publication Types

Not every publication needs the same depth. Use three tiers.

| Type | Length | Use Case | Example |
|---|---:|---|---|
| Field Note | 3-5 pages | Early observation, pattern, or micro-framework | "Five Signals That a Hospitality System Is Losing Confidence" |
| Field Guide | 8-16 pages | Main downloadable framework or scorecard | "Architecture of Confidence Field Guide" |
| Practice Report | 18-40 pages | Flagship research synthesis or annual publication | "Environmental Systems Design OS: Practice Report" |

The Field Guide is the core format. Field Notes can feed guides. Practice Reports can collect and expand them.

## Standard Table Of Contents Template

Use this table of contents for most 8-16 page guides.

| Section | Purpose |
|---|---|
| 01. Cover | Name the framework, domain, and practice. |
| 02. Executive Thesis | State the central argument in one page. |
| 03. Why This Matters Now | Explain the business, operational, environmental, or product pressure. |
| 04. Field Context | Show where the insight came from: observation, client work, prototype, domain research. |
| 05. Core Framework | Present the reusable model. |
| 06. Diagnostic Lens | Convert the framework into evaluative dimensions. |
| 07. Pattern Library | Name recurring patterns, failure modes, or opportunity signals. |
| 08. System Map | Show relationships between actors, signals, layers, and decisions. |
| 09. Application Scenarios | Demonstrate how the framework behaves in realistic situations. |
| 10. Scorecard / Worksheet | Provide a lightweight tool the reader can apply. |
| 11. Implementation Path | Explain how the guide becomes action. |
| 12. Consulting Bridge | Translate the method into available engagements. |
| 13. Resources / References | Link to related projects, diagrams, case studies, and further reading. |
| 14. Closing CTA | Invite a scoping call, audit, workshop, or project conversation. |

## Page-By-Page Content Model

### Page 01: Cover

Purpose: Make the publication feel like a serious practice artifact, not a blog post.

Required fields:

- Guide title
- Subtitle
- Practice name: Dan Meier, Independent Systems Design Practice
- Publication type: Field Guide, Field Note, or Practice Report
- Version and date
- Primary domain tags
- Canonical URL

Recommended layout:

- Large title
- One-sentence thesis
- Small taxonomy strip
- Quiet visual signal from the framework: map, diagram crop, grid, or field texture

### Page 02: Executive Thesis

Purpose: Give a busy reader the entire argument quickly.

Content blocks:

- Thesis statement
- Who this is for
- What problem it helps diagnose
- What the reader will be able to see after reading
- What the guide does not claim

Writing rule:

Use direct strategic language. Avoid inflated claims. The guide should feel precise, useful, and bounded.

### Page 03: Why This Matters Now

Purpose: Establish urgency without hype.

Content blocks:

- Current pressure
- Why common approaches fail
- Where systems complexity appears
- What changes when this lens is applied

Example pressure categories:

- AI systems are making recommendations without enough traceability.
- Outdoor hospitality systems are becoming more operationally complex.
- Destination experiences must handle uncertainty, weather, staffing, and guest confidence.
- Digital products increasingly depend on physical-world context.

### Page 04: Field Context

Purpose: Anchor the guide in evidence.

Content blocks:

- Origin story of the framework
- Source materials: field observation, case study, prototype, research synthesis
- Evidence level: conceptual, field-informed, prototype evidence, shipped client evidence, operational validation
- Known limits

Recommended evidence callout:

| Evidence Source | Role |
|---|---|
| Field observation | Shows real-world behavior and environmental friction. |
| Prototype | Shows how the framework behaves in an interface or system. |
| Client work | Shows delivery capability and implementation realism. |
| Research synthesis | Shows conceptual grounding and pattern recognition. |

### Page 05: Core Framework

Purpose: Present the central model.

Content blocks:

- Framework name
- Plain-language definition
- 3-7 framework components
- One diagram
- Short explanation of how components interact

Framework rule:

If a model has more than seven named parts, split it into layers. Field guides should clarify complexity, not perform complexity.

### Page 06: Diagnostic Lens

Purpose: Translate the framework into evaluative questions.

Content blocks:

- Diagnostic dimensions
- Questions for each dimension
- Warning signs
- Indicators of maturity

Example structure:

| Dimension | Diagnostic Question | Warning Sign | Mature Signal |
|---|---|---|---|
| Signals | Does the system tell people what matters now? | Important context is hidden. | Relevant signals surface at the decision point. |
| Recovery | What happens when the first plan fails? | The user has no graceful next step. | Alternate paths are visible and trusted. |

### Page 07: Pattern Library

Purpose: Name the repeatable situations the guide helps readers recognize.

Content blocks:

- 5-9 named patterns
- Short description
- Where it appears
- Why it matters
- How to respond

Pattern naming rules:

- Use memorable but plain names.
- Prefer operational clarity over cleverness.
- A reader should understand the pattern before reading the description.

### Page 08: System Map

Purpose: Show the relationships beneath the framework.

Content blocks:

- Actors
- Signals
- States
- Decision points
- Feedback loops
- Failure modes
- Recovery paths

Visual rule:

One system map should explain one system. If the map requires extensive narration to decode, the map is not ready.

### Page 09: Application Scenarios

Purpose: Prove that the framework can travel across contexts.

Content blocks:

- Scenario title
- Context
- System friction
- Framework interpretation
- Response pattern
- Resulting design implication

Recommended number:

Use three scenarios:

- One physical/environmental scenario
- One service/operations scenario
- One digital/product scenario

### Page 10: Scorecard / Worksheet

Purpose: Give the reader a practical tool.

Content blocks:

- Instructions
- 5-8 score dimensions
- 1-5 scoring scale
- Evidence notes
- Interpretation guide
- Recommended next action

Scorecard rule:

The scorecard should not pretend to be scientific if it is a strategic diagnostic. Label it as a structured reflection or preliminary audit unless validated through repeated use.

### Page 11: Implementation Path

Purpose: Show how insight becomes action.

Content blocks:

- Step 1: Read the system
- Step 2: Locate the friction
- Step 3: Name the pattern
- Step 4: Map the decision logic
- Step 5: Design the recovery path
- Step 6: Test against field conditions
- Step 7: Convert into backlog, specification, prototype, or service change

### Page 12: Consulting Bridge

Purpose: Connect the publication to hireable services.

Content blocks:

- Relevant engagement type
- What the guide helps prepare
- What a paid engagement would add
- What the client receives

Map to current services:

| Guide Output | Service Fit |
|---|---|
| Diagnostic scorecard | Systems Audit |
| Signal/state/recovery model | Adaptive Logic Framing |
| Framework-to-product structure | Structural Design Strategy |

### Page 13: Resources / References

Purpose: Turn the guide into a node in the broader Practice OS.

Content blocks:

- Related portfolio projects
- Related frameworks
- Case-study proof
- Diagrams
- Further reading
- Version history

### Page 14: Closing CTA

Purpose: Give a clear next step without making the guide feel like a sales deck.

CTA hierarchy:

1. Primary: Book a scoping call
2. Secondary: Explore the related framework
3. Tertiary: Read the professional validation case studies

Recommended CTA copy:

> If this guide describes a system you are trying to understand, the next step is a scoped systems audit.

## Diagram Types

A strong guide library needs a repeatable visual grammar. Use these diagram types across publications.

| Diagram Type | Purpose | Best For |
|---|---|---|
| Framework Model | Shows the named parts of a method | Architecture of Confidence, Trust Framework |
| Layer Stack | Shows system layers from physical to digital to operational | Environmental Systems OS, HADE |
| Signal Map | Shows inputs, context, and environmental cues | Responsive Ecologies, Wayfinding Matrix |
| Decision Flow | Shows choices, confidence, and next steps | AI trust, guest guidance, service recovery |
| Feedback Loop | Shows how the system learns or adapts | AI products, stewardship systems |
| Failure Mode Map | Shows where systems break | Audits, case-study validation |
| Recovery Path | Shows what happens after uncertainty or failure | Confidence, hospitality, operations |
| Evidence Chain | Shows source-to-recommendation traceability | Trust Frameworks for AI |
| Maturity Matrix | Shows levels of capability or readiness | Consulting diagnostics |
| Field Scenario Walkthrough | Shows a realistic situation over time | Outdoor hospitality, destination systems |

## Visual Hierarchy

Use a consistent hierarchy so every guide feels like part of the same publication system.

| Level | Visual Treatment | Purpose |
|---|---|---|
| Publication title | Large serif, minimal supporting copy | Establish authority and topic. |
| Section heading | Serif or strong sans, numbered | Make the document easy to scan. |
| Framework term | Bold or small caps | Signal reusable vocabulary. |
| Diagnostic question | Prominent callout | Pull reader into application. |
| Evidence note | Small bordered box | Separate proof from interpretation. |
| Diagram | Full-width or centered | Carry the conceptual load. |
| Worksheet | Table or form-like block | Encourage application. |
| CTA | Quiet but clear band | Move reader to the next step. |

Design principles:

- Keep diagrams black, neutral, amber, teal, or one domain-specific accent.
- Avoid decorative gradients.
- Use generous margins and readable line lengths.
- Favor annotated diagrams over ornamental graphics.
- Every visual must teach, diagnose, or summarize.

## Writing Style Guide

### Voice

Use a calm, precise, founder-level consulting voice.

The guide should sound like:

- A field researcher who can synthesize evidence
- A systems designer who can name structure
- A consultant who knows what implementation requires
- A practitioner who avoids false certainty

### Sentence Style

Prefer:

- Short declarative thesis sentences
- Specific nouns
- Bounded claims
- Concrete examples
- Plain language before terminology

Avoid:

- Hype
- Abstract grandeur
- Overuse of "future of"
- Generic innovation language
- Unqualified claims like "revolutionary" or "best-in-class"

### Claim Discipline

Every strong claim should be supported by at least one of:

- Field observation
- Prototype behavior
- Case-study evidence
- Research synthesis
- Clear conceptual reasoning

Use these evidence labels:

| Label | Meaning |
|---|---|
| Conceptual | Useful framework, not yet field-tested. |
| Field-informed | Grounded in observation or domain research. |
| Prototype-backed | Demonstrated through an interface, system, or build. |
| Delivery-backed | Supported by shipped professional work. |
| Operationally validated | Used repeatedly in real-world practice. |

### Naming Rules

Titles should follow one of these patterns:

- The [Framework Name] Field Guide
- A Field Guide to [System Problem]
- [Framework Name]: A Diagnostic Guide for [Audience]
- [Domain] Systems Field Guide: [Specific Lens]

Examples:

- The Architecture of Confidence Field Guide
- A Field Guide to Designing Trustworthy AI Recommendations
- Responsive Ecologies: A Diagnostic Guide for Adaptive Stewardship Systems
- Outdoor Hospitality Systems Field Guide: Guest Confidence and Recovery

## Future PDF Generation

Start with Markdown and static web pages. Add PDF generation after the first guide proves the format.

Recommended phases:

| Phase | Approach |
|---|---|
| 1 | Markdown source in `docs/resources/field-guides`. |
| 2 | Static resource landing pages in `app/resources/[slug]`. |
| 3 | Hand-exported PDF stored in `public/documents/field-guides`. |
| 4 | Automated PDF generation using a print stylesheet or a script. |
| 5 | Versioned downloads and archive pages. |

Do not automate PDF generation before the first two guides are stable. The risk is building tooling before the publishing voice is proven.

## Publishing Workflow

Use this sequence for every new guide.

1. Choose the framework or capability.
2. Define audience and use case.
3. Write a one-page executive thesis.
4. Identify evidence sources.
5. Draft the framework model.
6. Draft the diagnostic lens.
7. Create one scorecard or worksheet.
8. Add three application scenarios.
9. Connect to services.
10. Publish as Markdown internally.
11. Create a static resource page.
12. Export PDF only after the web version reads clearly.

## Quality Checklist

Before publishing, every guide should pass this checklist.

| Check | Question |
|---|---|
| Thesis clarity | Can the argument be understood in one paragraph? |
| Audience clarity | Is it clear who should read this? |
| Evidence clarity | Does the guide explain where the method comes from? |
| Framework clarity | Can the core model be remembered after reading? |
| Diagnostic utility | Can the reader apply at least one part immediately? |
| Visual usefulness | Does every diagram teach something specific? |
| Consulting bridge | Is the next paid engagement clear but not pushy? |
| Portfolio connection | Does the guide link back to related projects and proof? |
| Version control | Is status, date, and version clear? |
| Static compatibility | Can the guide exist as static Markdown, static page, and PDF? |

## What Not To Build Yet

Do not build these until at least two guides are published:

- Complex resource filtering
- Gated downloads
- Email capture automation
- Paid product library
- Automated PDF generation
- Full MDX component library
- CMS-backed guide authoring

The first goal is not scale. The first goal is a format that feels credible, useful, and repeatable.

## Final Recommendation

The Field Guide Publishing System should become the public-facing publication layer of the Independent Systems Design Practice.

The strongest first move is to create the system now, then publish one flagship guide using it:

**The Architecture of Confidence Field Guide**

That guide should act as:

- A consulting pre-read
- A downloadable practice artifact
- A framework proof point
- A bridge between research, services, and professional validation
- The template for the future publication library

Once the first guide is working, the same structure can support Environmental Systems Design OS, Responsive Ecologies, Trust Frameworks for AI, and future methods without reinventing the format each time.
