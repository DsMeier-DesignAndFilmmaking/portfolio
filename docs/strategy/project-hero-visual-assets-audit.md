# Project Hero Visual Assets Audit

Review lens: hero visuals only.

Goal: determine whether each hero visual improves comprehension, reduces comprehension, or asks the visitor to read too much before they understand the project.

This document evaluates illustrations, architecture diagrams, phone mockups, graphics, images, callouts, badges, labels, and annotations. It does not redesign pages or recommend implementation details.

## Visual Recommendation Types

- **Illustration:** A composed visual metaphor or environmental scene.
- **Architecture preview:** A restrained partial system diagram that signals structure without explaining the whole system.
- **Simplified diagram:** A reduced diagram with only the essential relationship or flow.
- **Photography:** A real or atmospheric image that clarifies place, product, client, or experience.
- **Abstract visualization:** A non-literal visual signal for system behavior, mood, or complexity.
- **Device mockup:** A UI/product surface shown in a phone, tablet, laptop, or app-frame context.
- **No hero visual:** Text-first hero where adding a visual would create false certainty or unnecessary noise.

## Visual Components That Usually Reduce Hero Comprehension

- Multiple badges or tags beside a dense visual.
- Diagram labels that repeat body copy.
- Status labels that require technical interpretation.
- Figcaptions in the first viewport.
- Interactive controls before the visitor understands the project.
- Animated connectors that draw attention away from the headline.
- Visuals with more than one focal point.
- Mockups with too many visible metrics, state chips, or debug-like labels.

## Visual Components That Usually Improve Hero Comprehension

- One clear product surface.
- One atmospheric image that matches the concept.
- One simplified relationship model.
- One restrained architecture preview.
- One client/product artifact that proves the work category.
- A visual that can be understood without reading every label.

- Product surface visuals with Surface_ID and generic explanatory text.

### Visuals That Feel Like Documentation Instead Of Presentation

- Dense architecture diagrams.
- Debug-like interface states.
- Signal/output cards.
- Full flow diagrams.
- Technical labels embedded into mockups.
- Scenario metadata beside technical visuals.

Documentation is valuable, but it should arrive after the hero establishes confidence.

## Recommended Visual System

Use a small set of visual rules rather than inventing a new visual strategy for every page.

### Rule 1: Research Pages Use Architecture Previews Or No Dense Visual

Use for:

- Environmental Systems Design OS
- Architecture of Confidence
- Trust Framework
- CATDS logic
- Relational Heuristics Engine

Recommended visual type:

- Architecture preview.
- Simplified diagram.
- No hero visual for especially abstract or early work.

### Rule 2: Experience And Place-Based Concepts Use Photography Or Illustration

Use for:

- Intention Engine
- Wayfinding Matrix
- Narrative Architecture
- Narrative Experience Generator

Recommended visual type:

- Photography.
- Illustration.
- Abstract visualization if the concept is not tied to a real place.

### Rule 3: Product Surfaces Use Device Mockups

Use for:

- Context-Aware Detours
- Social Opportunity Matching
- Narrative Experience Generator surface
- Healthcare if repositioned around forms/platform UX
- McDonald's Kiosk
- DoubleGood
- AdviseStream
- Sphere Software
- Nodalytics

Recommended visual type:

- Device mockup.
- Product surface crop.
- One clear UI state only.

### Rule 4: Complex System Concepts Use Editorial First, Visual Second

Use for:

- Responsive Ecologies
- HADE
- Spontaneity Engine
- Social Capital Orchestrator

Recommended visual type:

- Abstract visualization in hero.
- Full architecture diagram below fold.

### Rule 5: Client Proof Pages Use Large Visuals

Use for:

- Purdue
- TimberTech
- Intel
- Newdea where visual clarity is strong
- Havas if project-specific

Recommended visual type:

- Photography.
- Large product image.
- Device mockup when the work is more product/UI than brand/place.

## Final Recommendation

Most current hero visuals prove too much too soon. The portfolio should separate **presentation visuals** from **documentation visuals**.

Presentation visuals belong in the hero. They should create context, mood, or proof in one glance.

Documentation visuals belong below the fold. They should explain architecture, evidence paths, signal logic, and detailed flows after the visitor already understands why the project matters.

The strongest portfolio-wide shift is to replace dense right-column diagrams with restrained previews, photography, device mockups, or no visual at all depending on the project type.
