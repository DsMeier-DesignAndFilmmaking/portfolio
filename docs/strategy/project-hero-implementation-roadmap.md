# Project Hero Implementation Roadmap

Production refinement roadmap for the portfolio project hero system.

Scope: hero sections only.

Do not modify navigation, routing, or below-the-fold project architecture. Do not reduce technical credibility. The objective is to make the first viewport feel like a premium independent systems design practice rather than a collection of unrelated case studies.

## Executive Summary

The portfolio already communicates intelligence, originality, and systems depth. The main issue is that many hero sections try to prove the work too early. The first viewport often includes the project name, thesis, summary, status, tags, diagrams, captions, metadata, system logic, and proof artifacts all at once.

The biggest opportunity is not to remove depth. It is to sequence it.

Heroes should establish trust first:

1. What is this?
2. Why does it matter?
3. Why should I continue?

The proof should begin immediately after the hero, not inside the hero.

Across the portfolio, the strongest first impressions are the simplest: a clear title, one sharp sentence, and one restrained visual or artifact. The weakest first impressions are dense system pages where the user is asked to parse labels, diagrams, Challenge/Solution blocks, or technical metadata before understanding the project.

The refinement strategy is to create one shared hero system with controlled variants:

- Research publication.
- Editorial left / visual right.
- Editorial with visual below.
- Centered editorial.
- Full-width visual.
- Magazine-inspired.

This preserves project-specific personality while establishing a unified premium consulting-practice standard.

## Cross-Project Findings

### Recurring Patterns

- Many heroes use the same broad formula: breadcrumb, title, subtitle, long paragraph, status/tags, visual proof.
- Research pages often behave like product pages, using dense diagrams in the first viewport.
- Travel + AI logic pages often compress an entire case-study overview into the hero.
- Archived client work is structurally simpler and often communicates credibility faster than the research work.
- Product surface pages are promising but over-labeled with metadata such as Surface_ID and generic UX/UI explanation.

### Recurring Inconsistencies

- Some pages use shared navigation/header patterns, while others use custom hero/navigation treatments.
- Some project heroes use full-viewport visual drama; others are text-only and feel underpowered.
- Status and maturity language appears inconsistently: badges, cards, labels, or paragraphs.
- Visual treatment varies widely: photography, diagrams, SVG landscapes, interface mockups, system engines, and no visual.
- Similar concepts use different terms: confidence, guidance, context, signals, recovery, intelligence, framework, architecture.

### Recurring Strengths

- Project names are generally strong.
- The work has real conceptual depth.
- The portfolio has a distinctive systems-design point of view.
- Several visuals are valuable, especially when treated as second-scroll proof.
- Client work establishes professional credibility quickly.
- Research and concept pages show uncommon originality.

### Recurring Risks

- Heroes can feel like documentation instead of presentation.
- Dense visuals compete with headlines.
- Technical vocabulary appears before the plain-language premise.
- Tag and badge clusters make pages feel less premium.
- Long supporting paragraphs reduce seven-second comprehension.
- Full architecture diagrams above the fold can make the work feel harder to enter than it is.

## Hero Design Principles

### 1. Calm Before Complexity

The hero orients. The page proves. The first viewport should feel composed and intentional, not exhaustive.

### 2. One Primary Read

The project title must be the dominant first read on every project page.

### 3. One Secondary Read

Use one calm positioning sentence or one restrained visual as the clear second read. Avoid multiple competing secondary elements.

### 4. Presentation Before Documentation

Hero visuals should create context, mood, or proof in one glance. Documentation visuals belong below the fold.

### 5. Plain Language First

Technical credibility should remain, but technical vocabulary should be introduced after the visitor understands the project.

### 6. Status Without Noise

Use one short status or evidence-boundary line only when it prevents misunderstanding, such as "Concept, not a deployed product."

### 7. Project Personality Through Controlled Slots

Project-specific expression should come through visual type, accent color, tone, and one optional status line, not through custom hero architecture every time.

### 8. The Hero Earns The Next Scroll

A successful hero does not answer everything. It gives enough confidence to continue.

## Standard Hero Architecture

### Content Order

Every hero should use this content hierarchy:

1. Breadcrumb or eyebrow.
2. Project title.
3. One-sentence positioning statement.
4. Optional one-line status or evidence boundary.
5. Optional single CTA.
6. Optional restrained visual.
7. Hint of the next section where possible.

Do not include in the hero by default:

- Tag clusters.
- Multiple badges.
- Full captions.
- Challenge/Solution/Core Pillars.
- Scenario metadata.
- Detailed metrics.
- Full architecture diagrams.
- Debug labels.
- Multiple CTAs.

### Layout

Use six governed variants.

#### Variant 1: Research Publication

Best for frameworks, research systems, evidence systems, and logic-heavy concepts.

Use for:

- Environmental Systems Design OS.
- Architecture of Confidence.
- Trust Framework.
- CATDS logic.
- Relational Heuristics Engine.

Structure:

- Text-led.
- 7 to 8 columns of editorial content.
- Optional quiet architecture preview.
- Diagram/model begins below the fold.

#### Variant 2: Editorial Left / Visual Right

Best for product surfaces or simple artifact pairings.

Use for:

- Travel + AI product surfaces.
- Adaptive Outdoor Hospitality Companion, if the right visual is simplified.

Structure:

- 6 columns text.
- 6 columns visual.
- One clear UI or diagram preview.
- No dense metadata.

#### Variant 3: Editorial With Visual Below

Best for complex concepts whose visuals require more time.

Use for:

- Responsive Ecologies.
- HADE.
- Spontaneity Engine.
- Social Capital Orchestrator.

Structure:

- Text-first opening.
- Full-width visual proof begins below the opening or just after the first viewport.
- Hero visual may be abstract or absent.

#### Variant 4: Centered Editorial

Best for early, text-led, or high-restraint concepts.

Use for:

- Field Notes.
- Digital Executor.

Structure:

- Centered or narrow editorial block.
- No dense visual.
- Optional small status/proof line.

#### Variant 5: Full-Width Visual

Best for client work and strong visual proof.

Use for:

- Purdue.
- TimberTech.
- Healthcare, if paired with specific UI or project artifact.
- McDonald's Kiosk.
- Intel.
- Nodalytics.
- Newdea.
- DoubleGood.
- AdviseStream.
- Sphere Software.
- Havas.
- Rich Products.

Structure:

- Full-width or large background image.
- Concise overlay text.
- Client/project title.
- One proof sentence.
- Metrics and details below.

#### Variant 6: Magazine-Inspired

Best for place-based, experiential, or editorial concepts.

Use for:

- Intention Engine.
- Wayfinding Matrix.
- Narrative Architecture.
- Narrative Experience Generator, where appropriate.

Structure:

- Strong editorial title.
- Atmospheric image or illustration.
- Minimal labels.
- No figcaption in the first viewport.

### Spacing

Spacing should support editorial calm.

Recommended vertical rhythm:

1. Eyebrow.
2. Moderate gap.
3. Title.
4. Larger gap.
5. Supporting sentence.
6. Moderate gap.
7. Optional status or CTA.
8. Visual, if used.

Rules:

- Do not stack badges, tags, and CTA clusters under the title.
- Do not place dense bordered cards directly beside or below the headline.
- Increase breathing room between title and body copy where the title is long.
- Let the first body section carry proof and density.

### Typography

Hero typography should feel editorial, not dashboard-like.

Title:

- Largest text.
- Two to three lines max on desktop where possible.
- Avoid placing a full descriptive subtitle inside the h1 when it becomes a second headline.

Supporting sentence:

- One sentence.
- 18 to 28 words preferred.
- Plain language before technical terms.
- No repeated thesis/summary/callout pattern.

Eyebrow:

- Small and quiet.
- One line.
- Avoid multiple adjacent badges.

Status:

- One line.
- Plain language.
- Lower visual weight than supporting sentence.

CTA:

- One primary CTA only.
- Direct label.
- No decorative bracket styling if it adds visual noise.

### Visual Treatment

Visuals must support comprehension in one glance.

Preferred visual mapping:

| Project Type | Hero Visual Treatment |
| --- | --- |
| Research system | Architecture preview or no visual |
| Framework | Simplified diagram |
| Place-based concept | Photography or illustration |
| Experience concept | Photography, illustration, or abstract visualization |
| Complex system concept | Abstract visual in hero; full diagram below |
| Product surface | Device mockup or clean UI surface |
| Client case study | Full-width image, product artifact, or device mockup |
| Early-stage concept | No visual or quiet cue |

Move below the fold:

- Full architecture diagrams.
- Evidence paths.
- Interactive signal engines.
- Logic receipts.
- Scenario metadata.
- Dense captions.
- Multi-step proofs.

### Interaction

Hero interaction should be minimal.

Allowed:

- One CTA.
- Gentle scroll cue.
- Subtle visual motion if non-essential.

Avoid:

- Interactive controls required for comprehension.
- Tabbed or stateful system demos in the hero.
- Multiple CTAs.
- Animations that pull attention from the title.

### Responsive Behavior

Desktop:

- Preserve a 12-column grid.
- Keep title as dominant first read.
- Right-side visuals must be optically lighter than the title block unless using full-width client proof.

Tablet:

- Collapse or simplify dense visuals.
- Preserve title and supporting sentence.
- Keep status lines from wrapping awkwardly.

Mobile:

- Text first.
- One column.
- Hide or delay dense visuals.
- Use one CTA maximum.
- Move tags, metadata, captions, and proof blocks below.
- Ensure title line breaks feel intentional.

## Reusable Component Strategy

### Shared React Components

The following should become shared hero primitives:

- `ProjectHero`
- `HeroShell`
- `HeroEyebrow`
- `HeroTitle`
- `HeroSummary`
- `HeroStatusNote`
- `HeroAction`
- `HeroVisualFrame`
- `HeroImage`
- `HeroDeviceMockup`
- `HeroDiagramPreview`
- `HeroAbstractVisual`
- `HeroScrollCue`

### Shared Supporting Components Below Hero

These should be standardized but rendered below the hero:

- `ProjectMetadata`
- `ProjectTags`
- `EvidenceBoundary`
- `ChallengeSolution`
- `CorePillars`
- `ScenarioMetadata`
- `SystemDiagram`
- `VisualCaption`
- `MetricsStrip`

### Project-Specific Slots

Allowed hero slots:

- Accent color.
- Tone/background.
- Visual type.
- One project-specific visual.
- One status/evidence line.
- One CTA.
- One atmospheric cue.

Not allowed as default hero slots:

- Full tag lists.
- Multi-column metadata.
- Full architecture diagrams.
- Long captions.
- Challenge/Solution/Core Pillars.
- Scenario metadata.
- Multiple proof cards.

### Proposed `ProjectHero` Inputs

No code required, but implementation should plan for:

- `projectId`
- `variant`
- `eyebrow`
- `title`
- `summary`
- `statusNote`
- `primaryAction`
- `visual`
- `visualType`
- `tone`
- `breadcrumb`
- `background`
- `accent`

### Component Governance

The shared hero component should:

- Enforce title-first hierarchy.
- Limit above-the-fold slots.
- Support the six approved variants.
- Keep metadata below hero unless explicitly allowed.
- Provide responsive rules by variant.
- Support accessible headings and visual alt logic.

The component should not:

- Accept arbitrary dense children above the fold.
- Render unlimited badges/tags.
- Render multiple CTAs by default.
- Render full diagrams without deliberate override.

## Migration Plan

### Phase 1 — Quick Wins

Goal: reduce reading effort and visual noise without restructuring page architecture.

#### 1. Remove Or Move Repeated Hero Metadata

Apply across:

- Product surface pages.
- Travel + AI logic pages.
- Research pages with tag clusters.

Move below fold:

- Surface_ID.
- Tag clusters.
- Multiple status badges.
- Ownership labels.
- Scenario metadata.
- Figcaptions.

Expected impact:

- Immediate reduction in cognitive load.
- More premium first impression.
- Lower regression risk.

#### 2. Shorten Supporting Copy

Apply across:

- HADE.
- Responsive Ecologies.
- Field Notes.
- Digital Executor.
- Travel + AI logic pages.
- Archived client pages with generic descriptions.

Rule:

- One sentence, 18 to 28 words.
- Plain language first.
- One technical term max.

Expected impact:

- Better seven-second comprehension.
- Stronger hiring-manager first impression.

#### 3. Reduce Hero CTAs

Apply across:

- HADE.
- Travel + AI logic pages.
- Any hero with two CTAs.

Rule:

- One primary CTA maximum.
- Move secondary action below fold.

Expected impact:

- Less decision friction.
- Cleaner scan pattern.

#### 4. Suppress Captions And Dense Visual Labels Above Fold

Apply across:

- Wayfinding Matrix.
- Intention Engine.
- Product surfaces.
- Research visuals.

Expected impact:

- Visuals feel more like presentation, less like documentation.

#### 5. Sharpen Client-Work Hero Support Lines

Apply across:

- TimberTech.
- Healthcare.
- Nodalytics.
- Newdea.
- AdviseStream.
- Sphere Software.
- Havas.
- Rich Products.

Rule:

- Replace generic "improving UX" language with specific proof: IA, CMS, component library, product discovery, kiosk flow, dashboard prototype, workflow design.

Expected impact:

- Faster professional credibility.

### Phase 2 — Structural Improvements

Goal: align each project with the correct hero variant while preserving route and page structure.

#### 1. Convert Dense Right-Column System Visuals Into Second-Section Proof

Apply first to:

- Responsive Ecologies.
- HADE.
- Spontaneity Engine.
- CATDS logic.
- Relational Heuristics Engine.
- Social Capital Orchestrator.

Recommended shift:

- Hero becomes editorial-first.
- Dense architecture/system visual moves to the first body section or below hero.
- Hero visual becomes abstract preview, simplified diagram, or no visual.

Expected impact:

- Major clarity improvement.
- Stronger premium consulting feel.
- Preserves technical depth below the fold.

#### 2. Establish Research Publication Heroes

Apply to:

- Environmental Systems Design OS.
- Architecture of Confidence.
- Trust Framework.
- CATDS logic.
- Relational Heuristics Engine.

Pattern:

- Eyebrow.
- Title.
- One-sentence abstract.
- Optional one-line status/evidence boundary.
- Quiet preview or no visual.

Expected impact:

- Greater rigor.
- Less product-demo feel.

#### 3. Establish Magazine-Inspired Heroes

Apply to:

- Intention Engine.
- Wayfinding Matrix.
- Narrative Architecture.
- Narrative Experience Generator where appropriate.

Pattern:

- Editorial title.
- Atmospheric visual.
- Minimal labels.
- No first-viewport figcaption.

Expected impact:

- More expressive and premium.
- Better fit for experiential systems work.

#### 4. Establish Centered Editorial Heroes

Apply to:

- Field Notes.
- Digital Executor.

Pattern:

- Text-led.
- Strong title.
- One positioning sentence.
- Optional status line.

#### 5. Normalize Client Proof Heroes

Apply to:

Pattern:

- Client/project title.

- Metrics below fold.

Expected impact:

### Phase 3 — Design System Consolidation

Goal: replace one-off hero implementations with a governed shared system.

#### 1. Build Shared Hero Primitives

Create shared primitives:

- Eyebrow.
- Title.
- Summary.
- Status note.
- CTA.

- Image.

- Consistency.
- Lower future design debt.
- Easier QA.

#### 2. Implement `ProjectHero` Variants

Support six variants:

1. Research publication.
2. Editorial left / visual right.
3. Editorial with visual below.
4. Centered editorial.
5. Full-width visual.
6. Magazine-inspired.

Expected impact:

- Unified architecture without flattening project personality.

#### 3. Create Project Hero Content Model

Define a content model for hero data:

- Project title.
- Eyebrow.
- Summary.
- Variant.
- Visual type.
- Status note.
- CTA.
- Accent.
- Tone.

Expected impact:

- Less copy drift.
- Easier content review.
- Easier future project creation.

#### 4. Move Non-Hero Elements Into Shared Below-Fold Components

Standardize:

- Metadata.
- Tags.
- Evidence boundaries.
- Challenge/Solution.
- Core Pillars.
- Scenario details.
- Captions.
- Metrics.

Expected impact:

- Heroes remain clean.
- Technical credibility is preserved in structured sections.

#### 5. Add Hero QA Checklist

Before publishing, verify:

- Can a hiring manager answer "what is this?" in seven seconds?
- Is the project title the dominant read?
- Is the supporting sentence one sentence?
- Is there no more than one CTA?
- Are tags and metadata below the fold?
- Is the visual understandable without reading labels?
- Does the hero feel calmer than the body sections?
- Does the next section carry the proof?

Expected impact:

- Prevents regression into over-explained heroes.

## Final Implementation Guidance

The implementation pass should not begin by redesigning visuals. It should begin by reducing hero burden:

1. Remove non-essential metadata.
2. Shorten hero copy.
3. Move detailed proof below the fold.
4. Assign each page to a governed hero variant.
5. Consolidate shared hero primitives.

The desired final state is not minimalism for its own sake. It is controlled sequencing.

The portfolio should still feel technically deep, but the first viewport should feel calm, confident, and publication-ready.
