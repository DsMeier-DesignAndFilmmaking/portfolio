# Practice Framework Library

*The practice's recurring methods, documented once, in one reusable form.*

> **What this is, and is not.** The practice's frameworks are already inventoried and evaluated elsewhere — this does not repeat that work:
> - **IP-asset lens** (the 4-layer stack, per-asset status, priority scoring, IP roadmap) → `research-practice-ip-inventory.md`.
> - **Commercial lens** (seven named frameworks scored on business potential, format matrix, go-to-market roadmap) → `research-practice-framework-commercialization.md`.
> - **Structural lens** (the lineage graph, frameworks "hiding inside concepts") → `research-practice-architecture-review.md`.
>
> This document is the missing **method lens**: each recurring framework documented as a *usable method* — Purpose, Inputs, Outputs, Applications, Relationships, Future evolution — so it can be pulled off the shelf and applied to a new project. It synthesizes the material scattered across the three docs above; for commercial scoring and sequencing, go to them. It also supplies the one thing the commercialization doc flagged as missing: a clean one-line **job** for every framework.

Maturity tags carry the practice's own Evidence Boundary into the library: **Keystone** (proven, reused everywhere) · **Core** (structurally central, partly validated) · **Emerging** (real but under-validated) · **Latent** (documented, not yet field-tested).

---

## How the library is organized

Three families, mirroring the practice's IP stack:

- **I. Method frameworks** — how the practice makes knowledge.
- **II. The Confidence Stack** — the core reusable decision system that recurs across nearly every project.
- **III. Applied frameworks** — domain instantiations of the stack.

The Confidence Stack is the spine. It runs as a system:

```
        conditions
            │
      [ Signal Layer ]  sense → typed, graded signals
            │
     [ Decision Layer ] interpret signals + context → a confidence-scored next step
            │
   ┌────────┴─────────┐
[ Recovery Model ]  [ Bounded Authority ]
 design the failure   gate: system decides vs.
 path before it fails  human decides, by confidence
            │
   integrated & named by
   ▶ Architecture of Confidence ◀  (the keystone the whole stack expresses)
```

## I. Method frameworks

### Ground Truth  ·  *Keystone*
- **Purpose (the job):** turn field observation into validated, reusable frameworks — the loop by which the practice makes knowledge.
- **Inputs:** real-world observation across many settings; existing corpus; a live question worth proving.
- **Outputs:** a named framework, a proof (case/pilot), and a publishable finding — every pass emits all three.
- **Applications:** the meta-method behind every project; formalized in the research program's studies.
- **Relationships:** *runs on* Environmental Systems Design OS; *fed by* Field Notes; *disciplined by* Evidence Boundary; *produces* every framework in Families II–III.
- **Future evolution:** publish the method itself; mature the corpus so "41 countries" becomes a citable evidence base (research-agenda Theme 10).

### Environmental Systems Design OS (Evidence OS)  ·  *Keystone*
- **Purpose:** keep every claim traceable to its evidence — the running system that stores observations, artifacts, and their lineage.
- **Inputs:** system audits (orgs/products/destinations); field observations; typed research artifacts.
- **Outputs:** evidence-lineage records (Observation → Evidence → Artifact → Framework); an artifact taxonomy; confidence-labeled claims.
- **Applications:** the substrate under all research work; the credibility engine that lets any framework be trusted.
- **Relationships:** *instantiates* Ground Truth; *stores the outputs of* Field Notes; *supplies evidence to* every framework and to client-work validation.
- **Future evolution:** licensable "evidence OS" template for other studios (ip-inventory roadmap); a published account of the method.

### Field Notes  ·  *Core*
- **Purpose:** capture what a place teaches, in place, in a structure that can become a decision later.
- **Inputs:** in-field observation; geofenced/contextual triggers; the situation as it actually occurs.
- **Outputs:** structured notes (Situation → Local Insight → Suggested Moves → Why This Works); a reusable decision playbook; the primary-research corpus.
- **Applications:** the input layer for the whole pipeline; the pattern reused by Digital Executor and HADE.
- **Relationships:** *feeds* Environmental Systems Design OS; *seeds* the Signal and Decision layers with real patterns.
- **Future evolution:** the documented capture protocol + coded corpus — the practice's one honest pre-revenue task (research-program).

### Evidence Boundary  ·  *Keystone*
- **Purpose:** state plainly what is established and what is not — the honesty instrument that makes every other claim trustworthy.
- **Inputs:** any claim, framework, or artifact about to be shown.
- **Outputs:** an explicit "established / not claimed" pairing carried alongside the claim.
- **Applications:** every framework page, every proof, every hero — the practice's most differentiating recurring habit.
- **Relationships:** *governs* all frameworks; *the visual/editorial expression of* Principle 11 (`practice-design-principles.md`).
- **Future evolution:** becomes the standard component wherever a claim appears; the maturation tag in this very library is an instance of it.

## II. The Confidence Stack

### Architecture of Confidence  ·  *Keystone*
- **Purpose:** design decisions people trust and act on under uncertainty.
- **Inputs:** a decision moment; captured signals; interpreted context.
- **Outputs:** a confidence-scored recommendation across its dimensions (context clarity, timing fit, cognitive load, human validation, autonomy preservation, recovery path); the confidence lexicon and principles.
- **Applications:** reused by Responsive Ecologies, Adaptive Hospitality, Wayfinding, Digital Executor, HADE — the transferable core.
- **Relationships:** *integrates* the Signal, Decision, and Recovery layers; *governed by* Bounded Authority; *derived via* Ground Truth.
- **Future evolution:** validate concept → evidenced (research-program Study 1); a general theory of confidence under variable conditions, including a pure-digital transfer (research-agenda Theme 1 white space).

### Signal Layer (Signal Matrix)  ·  *Core*
- **Purpose:** turn changing conditions into typed, graded signals a system can act on.
- **Inputs:** environmental and contextual conditions — weather, terrain, timing, crowding, load.
- **Outputs:** an ambient-signal taxonomy; graded signals mapped to guidance states (continue / prepare / reroute / recover / escalate).
- **Applications:** Wayfinding Matrix, Responsive Ecologies, CATDS (the sensing tier of HADE).
- **Relationships:** *feeds* the Decision Layer; *upstream of* Adaptive Guidance; *a layer of* Architecture of Confidence.
- **Future evolution:** a validated, low-sensor version that escapes the hardware/liability trap (research-agenda Theme 2 white space).

### Decision Layer (Decision Hierarchy + Confidence Assessment)  ·  *Core*
- **Purpose:** turn signals and context into a confidence-scored next step.
- **Inputs:** typed signals from the Signal Layer; interpreted context; the decision's stakes and window.
- **Outputs:** a confidence score (weighted dimensions → bands → suppression rules); a decision routed by altitude (Strategic / Tactical / Operational / Field).
- **Applications:** Responsive Ecologies (its most operational form), CATDS, Architecture of Confidence.
- **Relationships:** *consumes* the Signal Layer; *hands off to* Recovery Model and Bounded Authority; *the interpretive core of* Architecture of Confidence.
- **Future evolution:** a standalone decision-confidence scorecard/instrument (ip-inventory: currently latent).

### Recovery Model (Recovery Architecture)  ·  *Core*
- **Purpose:** design the failure path before it fails.
- **Inputs:** the ways a plan or experience can break; the moment of disruption; trust at stake.
- **Outputs:** a recovery path (steps + triggers); a recovery playbook; failure-cascade maps.
- **Applications:** Digital Executor, Adaptive Hospitality, Architecture of Confidence — a universal, under-exploited method.
- **Relationships:** *triggered by* the Decision Layer; *a component of* Architecture of Confidence; *proven by* client work in service recovery.
- **Future evolution:** validate against real disruption (research-program Study 3); a recovery playbook toolkit tied to churn/trust cost.

### Bounded Authority  ·  *Emerging (highest-value latent IP)*
- **Purpose:** decide what the system may decide, and gate the rest to a human by confidence.
- **Inputs:** a decision, its confidence score, and its stakes; the map of who holds authority.
- **Outputs:** an authority routing (system-decides / human-confirms / human-decides) with named escalation; suppression rules for low-confidence action.
- **Applications:** Responsive Ecologies (where it is currently buried); the practice's most timely, most transferable governance method.
- **Relationships:** *gates* the Decision Layer; *the governance expression of* Principles 7–8 (judgment over automation; preserve agency); *extract candidate* per the architecture review.
- **Future evolution:** extract, name, and reposition into the AI-governance market — the single highest-value packaging move in the practice (framework-commercialization); give it a credible origin via Study 4.

## III. Applied frameworks

### Adaptive Guidance  ·  *Emerging*
- **Purpose:** surface the right guidance at the right moment without turning the experience into an interface.
- **Inputs:** Signal Layer states; the person's situation and readiness (not identity).
- **Outputs:** ambient guidance modes; the decision to speak, stay silent, reroute, or escalate.
- **Applications:** Wayfinding Matrix; the guidance surface of HADE.
- **Relationships:** *consumes* Signal + Decision layers; *sibling to* Trust & Provenance (both shape what a system says); *bounded by* Bounded Authority.
- **Future evolution:** a non-screen/ambient pilot with an operator; a unified physical-digital orientation model bridging the client IA work (research-agenda Theme 3).

### Transformation Blueprint  ·  *Core*
- **Purpose:** translate what a person is seeking into spatial, sensory, and service choices.
- **Inputs:** self-described intention; an affordance library; the environment's possibilities.
- **Outputs:** a 9-dimension experience blueprint; an intention→environment translation; a 6-principle ethics frame (consent, explainability, data minimization, cultural fit, psychological safety, limits of inference).
- **Applications:** Intention Engine; a directly billable blueprinting deliverable today.
- **Relationships:** *applies* Architecture of Confidence to experience; *sibling to* Adaptive Hospitality Blueprint.
- **Future evolution:** field-validate the intention taxonomy against real guest language — its highest source-credibility risk (evidence-audit; research-agenda Theme 6).

### Trust & Provenance Model  ·  *Emerging*
- **Purpose:** verify that a recommendation is current, sourced, and credible before it is shown.
- **Inputs:** a recommendation and its origin; freshness, source, and credibility signals.
- **Outputs:** a verification verdict + provenance trail; a trust/verification layer other systems call.
- **Applications:** Trust Framework for AI Travel; a required layer inside HADE, CATDS, Responsive Ecologies.
- **Relationships:** *a specialization of* Evidence Boundary for live recommendations; *gates* Adaptive Guidance; *kin to* Bounded Authority (both are trust infrastructure).
- **Future evolution:** a portable provenance/traceability standard across domains (research-agenda Theme 8 — the AI-governance white space).

### Adaptive Hospitality Blueprint  ·  *Core (composed)*
- **Purpose:** run guest experience on read conditions and designed recovery, not fixed scripts.
- **Inputs:** guest intent; environmental signals; operational capacity; stewardship limits.
- **Outputs:** an operations service blueprint; a signal map; a recovery-as-hospitality path.
- **Applications:** Adaptive Outdoor Hospitality Companion — the beachhead and nearest recurring revenue.
- **Relationships:** a *composition* of Signal Layer + Decision Layer + Recovery Model applied to hospitality; *feeds* Responsive Ecologies.
- **Future evolution:** validate via a real operator pilot; the Outdoor-Hospitality Experience Standard + annual report (research-program Study 5).

*Peripheral method, documented for completeness:* **Relational Heuristics** (when a nearby connection is worth surfacing — Social Capital Orchestrator, RHE) is *Latent* and least on-thesis; held as an option, not a supported library method (research-agenda Theme 7).

## Using the library

- **A framework is "in the library" when it can state its job in one sentence, name its inputs and outputs, and point to a project that uses it.** Anything that can't is still a concept, not a method.
- **Build new work by composing, not inventing.** Most new projects are a domain application of the Confidence Stack plus one or two applied frameworks — the way Adaptive Hospitality Blueprint composes Signal + Decision + Recovery. Reach for composition before a new framework.
- **Every framework carries its Evidence Boundary.** The maturity tag is not decoration; a *Latent* framework may be used in a concept but not sold as proven. This is how the library refuses to overclaim.
- **Relationships use the narrative grammar.** "Feeds / applies / gates / sibling / extract" are the same edge types defined in `practice-narrative-architecture.md`, so the library and the story describe the frameworks the same way.

*For which frameworks to package, price, and publish first, and in what order, see `research-practice-ip-inventory.md` and `research-practice-framework-commercialization.md`. This library defines what each method* is *and* does*; those define what each is* worth *and* when *to sell it.*
